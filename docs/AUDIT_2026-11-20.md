# Shining Vacation Homes - full-site audit and launch handoff

**Review date:** 20 November 2026. **Scope:** all 14 content routes, shared components, enquiry backend, email delivery, encrypted storage, deployment configuration and dependencies.

## Decision

**The application is verified locally. Public launch is blocked by hosting and production configuration.** It would be inaccurate to call the live deployment ready or promise a perfect/security-certified website.

The public Vercel URL returned HTTP **402** with `X-Vercel-Error: DEPLOYMENT_DISABLED` on the homepage, contact page and enquiry API. The response body says `Payment required`. This is a hosting/account condition. The exact account trigger cannot be established without authenticated Vercel access. Check the team's Usage, Billing and project status; inspect Vercel's notification before taking the account-specific restore action. No plan upgrade, payment, limit increase or account change was performed by this audit.

GitHub still records the 18 November failed deployment for commit `8a60050`. Its private build logs remain inaccessible through the current session. Vercel was offered for reconnection, but a connection has not been confirmed. Public HTTP evidence is current; the earlier build-log error is historical.

The local release validator currently reports missing `ENQUIRY_ORIGIN`, a valid `ENQUIRY_DATA_KEY`, and persistent storage configuration. This establishes the local environment state, not the current contents of Vercel's private environment settings.

## 1. UI/UX, visual design and accessibility

### Strengths

- The cream, ink and blue palette, local typefaces and original logo/favicon form a consistent editorial identity. Desktop screenshots show contained chapter tabs, balanced image/copy columns, clear form boundaries and aligned navigation.
- The chapter section stacks image, tabs and content at tablet/mobile widths. No horizontal document overflow or broken loaded images appeared in the route/viewport scans or the additional breakpoint checks.
- Chapter keyboard navigation works with arrows, Home and End. The active state and panel relationships are exposed through tabs, selection state and ARIA relationships. Switching chapters preserves section height.
- FAQ buttons expose expanded state and region relationships; expansion reserves space instead of shifting the following section. Mobile navigation opens/closes and Escape restores focus to the menu button.
- The native photo dialog supports previous/next and Escape, remains within the viewport horizontally and now restores focus to its opener. There are no zoom controls or back-to-top overlays.
- The desktop enquiry sidebar remains centered while scrolling and stops inside the contact section. The form stacks at narrower widths. Optional preferences are disclosed progressively.
- Form labels, error relationships, live feedback, focus indicators, required field semantics and a skip link are present. Tests verify errors preserve typed data and reveal accessible feedback.

### Remaining limits and actionable work

- Full motion remains enabled, including when the operating system requests reduced motion, because this is the owner's explicit chosen behavior. Automated axe checks do not resolve motion sensitivity. An accessibility-oriented release should honor that system preference; this audit has not changed the approved motion behavior.
- Chromium at multiple viewport widths does not certify physical iOS/Safari or Android/Firefox behavior. Complete one real-device keyboard/touch and assistive-technology review before claiming broad browser or accessibility compliance.
- Accommodation photos are illustrative. Genuine team/service imagery and verified business proof could improve trust; do not invent property ownership, inventory, licences or reviews to fill the gap.

**Score: 8.5/10** for the local implementation, with the motion/accessibility limit explicitly retained.

## 2. Performance and technical architecture

### Strengths

- Next.js 16.4.6 App Router and React 19.3.1 prerender content pages. The enquiry route runs server-side. Internal routes use Next Link and fonts are local.
- Images use local originals with responsive Next Image sizes and WebP optimization. Runtime checks returned 256px and 384px WebPs of 7,498 and 13,438 bytes for the sampled image. The gallery is loaded only when opened.
- Server-rendered heading masks avoid rewriting the heading during hydration. Browser tests recorded no uncaught page errors across the content routes. Chapter/FAQ geometry is stable.
- The framework and mail/storage runtime packages match current stable registry tags at review time. No Three.js/WebGL runtime is present or needed.

### Lab measurements

Three fresh browser-context homepage runs per profile were measured against the local production server, with browser cache disabled. The mobile profile used 390x844, DPR 2, touch/mobile emulation, 150 ms latency, 1.6 Mbps down, 750 Kbps up and 4x CPU slowdown. Server-side image caches were already warm.

### Remaining work

- Restore the public deployment, then measure the final domain under real network conditions. Add owner-approved real-user monitoring if field performance needs continuous measurement.
- Confirm cache behavior and database connection latency on the selected host. Local SQLite tests do not establish PostgreSQL performance or TLS connectivity.
- Keep the shared header/layout and existing image sizing. There is no evidence that a large visual rewrite or more animation would improve the measured behavior.

**Score: 8.5/10** for the measured local implementation; production availability is separately blocked.

## 3. Security and data privacy

### Strengths and fixes

- No known dependency vulnerabilities were reported by the final npm audit; direct dependencies are not outdated. Dependency versions are pinned and the lockfile is committed. Dependabot checks weekly.
- POST-only JSON boundaries, strict origin checks, a 16 KiB limit, the new read deadline, input allowlists, lengths/date validation and the honeypot reduce malformed requests. These checks do not authenticate a visitor or replace anti-bot protection.
- SMTP uses the configured sender/recipient, verified TLS, fixed Gmail host and bounded send time. File and URL access through Nodemailer are disabled. Email HTML escapes user content; user data does not select arbitrary delivery hosts or recipients.
- Enquiries are captured before email delivery. AES-256-GCM protects stored payloads, HMAC identifiers avoid plain email indexes, SQL values are bound separately, and transactions enforce shared quotas and durable duplicate detection.
- Missing storage or delivery configuration fails truthfully. A saved enquiry with uncertain email delivery is described as saved, not as a confirmed reservation or inbox receipt.
- Locally verified response headers include HSTS, nosniff, frame blocking, referrer/permissions policies and CSP. Private env/data files are not served or committed.

### Remaining production risks and fixes

1. **Hosting access:** restore the disabled deployment through the Vercel account. Review the actual usage/billing notification; do not assume a code edit can clear the restriction.
2. **Production secrets/storage:** configure the actual HTTPS origin, Google App Password, PostgreSQL URL and stable encryption key. Back up the key securely; changing it makes existing encrypted records unreadable.
3. **Flood protection:** configure and verify Vercel edge rate limits/bot protection for `/api/enquiry/`. An attacker can spoof an Origin header outside a browser, and application sending budgets alone cannot stop request floods or quota exhaustion.
4. **CSP:** inline scripts/styles remain permitted for the current static/hydrated Next.js output. A strict nonce/hash policy is a separate rendering change that needs compatibility/performance testing. This audit does not label the current policy strict or claim complete XSS prevention.
5. **Operations:** schedule/assign enquiry cleanup, check failed-delivery records, secure operator mailboxes with MFA and confirm backup/retention access. Expired records are excluded from reads and pruned on capture/manual cleanup; automatic independent daily cleanup is not configured by this review.
6. **Verification:** current production PostgreSQL/TLS, mailbox receipt, hosting firewall rules and effective deployed headers remain unverified. No intrusive remote penetration testing, account security certification or legal compliance certification is claimed.

**Score: 8/10** for source/runtime safeguards. Production controls and end-to-end delivery are release requirements.

## 4. Technical SEO and discoverability

### Strengths

- All 14 routes have unique titles/descriptions, a single H1, semantic content and canonical tags. Internal navigation and guide links are crawlable.
- The sitemap includes the content routes. Robots allows content and disallows the API. Missing paths return 404 rather than the homepage.
- Organization, WebSite/WebPage and breadcrumb markup match the enquiry/showcase model. The site does not invent individual rental listings, availability, review aggregates or prices for accommodation it does not hold in inventory.
- Image alternative text and captions explain the illustrative nature of the photography. Open Graph/social metadata is page-specific.

### Launch actions

- The public HTTP 402 response prevents the hosted pages from being fetched normally. Restoring availability is the highest-priority SEO action.
- Set `NEXT_PUBLIC_SITE_URL` and `ENQUIRY_ORIGIN` to the approved final HTTPS origin, and ensure alternate domains redirect consistently. The current default points at the original business domain; ownership/DNS cutover must be confirmed before replacing the original site.
- After launch, verify the production robots/sitemap/canonicals and submit the final sitemap through the owner's Search Console. A public audit cannot prove Google index coverage or ranking.
- Add only verified company/location details and genuine service proof when the owner supplies them. Do not add fake addresses, review counts or inventory schema for SEO.

**Score: 8/10** for local technical SEO. Current public availability prevents launch/indexing approval.

## 5. Conversion and content quality

### Strengths

- The value proposition explains the actual service: share requirements and the team will discuss available accommodation. No instant inventory, checkout or fake reservation is implied.
- Repeated Plan your stay/enquiry actions lead to the appropriate section or contact route. Collection preference and guest context survive the contact link.
- The form asks for only name/email plus travel plans as essential guest information; exact dates, phone, area, accommodation and budget are optional. Owner enquiries omit disabled guest fields.
- Error/503 responses preserve input. Successful capture produces a clear reference and does not claim a reservation. Direct email/telephone contact is available as a fallback.
- Booking information asks visitors to verify the actual property, complete price and applicable terms before committing.

### Remaining work

- Current public downtime is a complete conversion blocker even though the local funnel works.
- Complete one approved, tagged production enquiry and confirm both the stored record and receipt in the team's inbox. Mocked UI submissions are not a substitute.
- Obtain owner approval of the final business identity, privacy wording, processor/retention arrangements, photography rights and confirmation terms. Do not promise an unverified response time or invent testimonials.
- Actual lead conversion and abandonment rates are unknown. Add measurement only after the owner approves the tool and any privacy requirements.

**Score: 8/10** for the local enquiry funnel; live conversion cannot be approved while hosting/delivery remain blocked.

## Top three actions before public launch

1. **Restore Vercel availability.** Connect the owner's Vercel account, review Usage/Billing and the disable notice, resolve the actual account condition and inspect the new deployment logs. A new Git commit alone will not clear HTTP 402.
2. **Complete production configuration.** Set the final origin, Gmail delivery values, managed PostgreSQL URL and stable 64-hex encryption key. Keep `check:release` enabled. Configure edge abuse protection and assign monitoring/cleanup.
3. **Deploy and verify one complete production journey.** Recheck all routes, headers, metadata, domain/HTTPS and responsive images. Submit an approved test enquiry, verify the saved record and actual inbox receipt, then secure owner approval of the published content and rights.

## Repeating the checks

Use Node 26.x. Run `npm ci`, `npm run build`, `npm test`, and `npm run test:browser`. On a machine without Chrome or a Playwright browser, run `npx playwright install chromium` first; Windows Chrome is detected when installed. `PLAYWRIGHT_CHROMIUM_EXECUTABLE` can point at an approved local browser. Browser tests start or reuse a localhost production server on port 4173 and intercept form submissions. Do not point this harness at a live customer endpoint.

`npm run check:release` validates the private release environment. `npm run check:email` verifies SMTP connection/authentication without sending email. Browser traces, screenshots and JSON logs are ignored in Git; use `test-results/browser-summary.json` for the local browser result. The source archive excludes real env files, customer data, logs, dependencies and build output.
