# Shining Vacation Homes — launch and security audit

Review date: 24 November 2026 (Pakistan time). Scope: all 14 public content routes, shared UI, Next.js configuration, enquiry API, delivery, encrypted storage, dependencies, browser assets, local Git history, and authenticated Vercel project metadata/build logs.

> Follow-up: the script CSP allowance, adapter snapshot failure, photograph delivery and network submission limits were addressed after this baseline audit. See [Release fixes](RELEASE_FIXES_2026-11-24.md) and [Adapter verification](ADAPTER_VERIFICATION_2026-11-24.json) for the updated evidence. Hosting readiness still requires independent verification.

## Launch decision

**Do not announce a public launch yet.** The local application passes the checks below, but the public deployment returns HTTP 402 with `X-Vercel-Error: DEPLOYMENT_DISABLED`. This is an observed hosting restriction. Its underlying billing, usage or account cause has not been established; no purchase, billing change, project unpause or deployment-protection change was made.

The latest deployment returned by the Vercel API is the failed 18 November deployment `dpl_6Ln3XfyPeKMPAhSAxFZTyaPbCpn2`, built from commit `8a60050`. Its logs show that the production configuration gate and Next compilation passed, then tests failed because generated `out/` HTML/sitemap files were absent. The current local build generates those files and passes their tests. A successful fresh Vercel build is still required; local success does not prove that Vercel's adapter/output handling is resolved.

All changes from this audit are local. They have not been pushed or deployed.

## Fixes implemented during this audit

| Finding | Change | Verification |
|---|---|---|
| An unset origin could fall back to a client-controlled Host header | The request URL is the fallback; a public production runtime requires ENQUIRY_ORIGIN. Browser requests marked cross-site are rejected. | Tests cover forged Host, missing configured origin, cross-site metadata and a correctly configured public origin. |
| Loopback naming could select the development storage path in a hosted request | Vercel always requires public storage configuration. A configured public origin cannot opt into local storage through a loopback request URL. | Regression verifies a Vercel loopback request fails before delivery when persistent storage is missing. |
| Next's local URL may use localhost while the browser uses 127.0.0.1 | Only loopback aliases with the same protocol and port are accepted when no public origin is configured, outside Vercel. No arbitrary Host trust is restored. | Unit regression covers allowed aliases, rejected ports/protocols/paths and public-origin isolation; a real preview API test checks the actual Next endpoint. |

Source changes: `src/enquiry-server.js`, `src/persistent-enquiry.mjs`. Security regressions: `tests/enquiry-server.test.mjs`, `tests/enquiry-store.test.mjs`, `tests/browser/site.spec.mjs`.

## 1. UI, UX and accessibility

Strengths:

- A consistent cream, ink and blue visual system, local fonts, responsive layouts and clear enquiry CTAs.
- Accommodation pages explain the types the team can arrange, without pretending to offer live inventory.
- Labels, required/optional information, inline field errors, keyboard navigation, dialog focus restoration, FAQ controls and chapter tabs are tested.
- Privacy and booking pages have a contents list that follows the reading position. Booking-to-contact navigation and browser Back are covered.
- The no-JavaScript form cannot submit user details through a GET request; direct email remains available.

Remaining work:

- Full motion is forced by the owner's explicit preference. This overrides an operating-system reduced-motion preference. It remains an accessibility limitation; it was not silently changed during this audit.
- Automated checks do not establish WCAG/ADA conformance. Manual screen-reader, zoom/reflow and Safari/Firefox checks remain outside the verified coverage.
- Have the client approve the newly written booking guidance and privacy arrangements.

**Score: 8/10.**

## 2. Performance and architecture

The verified local Node runtime is 26.13.1, the Node 26 LTS security release published on 11 November. Vercel targets Node 26.x; its exact deployed patch must be verified after a successful build. Next.js 16.4.6, React/React DOM 19.3.1, Nodemailer 10.6.1 and PostgreSQL client 4.1.1 are pinned. Content pages are prerendered; email and data access stay on the server. Internal routes use Next Link. Photographs use Next Image with responsive widths; fonts are local, and the gallery is loaded separately. There is no WebGL/Three.js rendering to audit.

Directional cold-cache laboratory samples: Chrome, localhost, 150ms simulated network latency, approximately 1.6Mbps download, 4x CPU throttling, with the browser regression suite running concurrently. These are single samples, not Lighthouse scores or real-user Core Web Vitals.

## 3. Security and privacy

Verified protections:

- POST-only JSON enquiries, explicit origin checks, cross-site metadata rejection, 16 KiB streaming body limit and a 10-second body-read deadline.
- Server-side allowlists, date validation, single-mailbox validation and rejection of header-like contact values.
- HTML email values are escaped; the message has a plain-text alternative. Injected URL preferences did not execute markup in the browser regression.
- SQL values use parameters. Website enquiry payloads use AES-256-GCM; fingerprints/rate-limit identifiers use keyed HMACs. Database transport requires certificate verification.
- Persistent capture occurs before delivery; concurrent duplicate submissions claim a single record. Provider failure never becomes an inbox-receipt claim.
- Durable quotas limit an email to five enquiries per 15-minute bucket, all enquiries to 20 per bucket and 80 per day. A bot can still exhaust these shared budgets; this is not comprehensive bot/DDoS prevention.
- Gmail uses TLS with certificate validation; Nodemailer's filesystem/URL attachment access and debug logging are disabled. Resend remains an optional server-side provider.
- Runtime headers include CSP, frame denial, nosniff, referrer policy, HSTS and restrictions on camera/microphone/geolocation. X-Powered-By is absent.
- Probes for environment files, the local database, Git configuration, package/source files and arbitrary external Next Image targets did not expose those resources. Production browser source maps are not enabled in configuration.
- No public administrator login or enquiry-record reader was found. Operator record access is a local CLI action. No card processing is implemented.

Remaining risks and actions:

1. CSP retains `script-src 'unsafe-inline'` and inline styles for the current static Next rendering. This weakens defence against injected inline scripts; a nonce/hash design should be considered with the caching/rendering tradeoff documented. Do not remove the directive blindly and break hydration.
2. Vercel reports no custom firewall configuration. Default protection applies, but a route-specific edge limit/challenge should be configured for POST `/api/enquiry/` before substantial public traffic. Origin checks are not bot authentication.
3. A real production PostgreSQL capture/read, Gmail authentication and approved inbox test remain unverified. This audit sent no external enquiry messages.
4. Keep the encryption key backed up separately from the database. Arrange record cleanup and monitoring of enquiries marked `attention`; mailbox retention is a separate process.
5. The secret checks covered current configured private values and selected patterns. They do not prove every possible historical or rotated credential has been detected.

No confirmed critical/high application vulnerability was found in the reviewed code and tested paths. That is a bounded audit result, not a penetration-test certificate or a guarantee.

**Score: 7.5/10.**

## 4. SEO and discoverability

Strengths: all 14 routes have unique titles/descriptions, a single H1, internal destinations, canonicals and sitemap entries. Robots allows the site and excludes the API. Organization/WebSite/WebPage and breadcrumb data describe the business without fabricated ratings or individual live inventory. Image descriptions and enquiry-oriented copy are present.

Before launch, align NEXT_PUBLIC_SITE_URL, ENQUIRY_ORIGIN and the actual client-approved HTTPS domain, then verify rendered canonicals, Open Graph URLs, redirects, robots and sitemap on that domain. The existing WordPress domain and the Vercel project are different deployments; this audit did not alter DNS. Only `shiningvacationhomes.vercel.app` is currently attached to the Vercel project. Search Console and indexing status were not verified. Hosting errors currently prevent the public deployment being assessed as a healthy crawlable site.

**Score: 8/10.**

## 5. Conversion and content accuracy

The site now supports the agreed requirement-led service: show accommodation styles, collect requirements, then discuss actual available options. Guest/monthly and owner enquiries are distinct. Direct email/telephone routes remain available. No instant reservation or payment is implied.

The brand, six accommodation categories, contact email, both telephone numbers and rental-management service match the original website. Editorial headlines, planning guides, FAQs, booking guidance and implementation-specific privacy text are newly written; they are not verified original company policies. Photo presence on the original website does not prove media rights or current availability. The original's prices and income-increase claim were intentionally not carried into this enquiry-led version.

Client approval of photo usage, the enquiry response process, privacy handling and individual booking/management terms remains necessary. Do not publish specific refund deadlines, deposits, amenities, yields or response promises without confirmation.

**Score: 7.5/10.**

## Top three actions before publication

1. **Restore hosting and prove a successful current deployment.** Investigate the account's DEPLOYMENT_DISABLED notice, resolve its actual cause, publish the reviewed source through the normal Git/deployment flow and require a READY result. Investigate generated test-artifact paths on Vercel if the historical ENOENT failures recur; do not bypass tests or the release gate.
2. **Verify the public domain and the real enquiry chain.** Review Vercel's authentication scope (`all_except_custom_domains`), confirm anonymous visitors can access the intended production domain, align origin/canonical settings, verify PostgreSQL capture and run one approved form-to-inbox test from the deployed site. Metadata-only environment checks are not proof of working credentials.
3. **Complete operational and client approval.** Add appropriate edge protection for enquiry traffic, establish failed-delivery/retention monitoring, confirm media rights and final policies, and measure production performance after the hosting issue is resolved.
